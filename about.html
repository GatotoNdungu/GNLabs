From the plant floor to the API layer

I started as a controls engineer, commissioning PLCs on factory floors where a bug doesn't throw a stack trace — it stalls a line, or worse. That environment teaches a particular kind of discipline: you define the failure modes before you write a single rung of logic, because the cost of guessing wrong is measured in downtime, not just an ugly changelog.

Over time the boundary between that world and the software world kept blurring. Plants wanted telemetry in the cloud. Dashboards needed to talk to fieldbus networks. Every project seemed to need one person who was fluent on both sides of the OT/IT line — and comfortable admitting when a "simple integration" was actually a control system problem wearing a software costume.

GN Labs is that role, formalized. I take on a small number of engagements at a time, work directly with the people who'll operate the system, and document everything to a standard where a second engineer could pick it up without a handover call. No account managers, no bench of juniors learning on your dime — just the person doing the work.

How the work gets done

Three habits carry across every engagement, regardless of whether the deliverable is a PLC program or a Python service.

01

Failure modes first

Before any logic gets written, we map out what happens when a sensor lies, a network drops, or an operator does the unexpected thing.

02

Model before you deploy

Control loops get simulated and hardware-in-the-loop tested before they ever touch live equipment. Hardware time is expensive; modeling time is cheap.

03

Document for a stranger

Every system ships with documentation written for an engineer who's never met me — because eventually, someone else will maintain it.
